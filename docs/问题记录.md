# 一、底盘（Chassis_2026）

## C-01 引脚三重冲突 ✅

- **发现阶段**：S0 上板前核对（2026-11-08 前后）
- **现象**：`tests/check_pins.ps1` 报 3 处重复：`GPIOB1`（`BIN1` 与 `E1B` 都占）、`GPIOB0`（`AIN2` 与超声波 `Trig`）、`GPIOA12`（循迹 `CH5` 与超声波 `Echo`）。
- **根因**：`pin_config.h` 是按 PCB 实际接线填的，而超声波当时还是旧设计的脚位（`Trig=PB0`、`Echo=PA12`），直接撞车。
- **解决**：
  1. `E1B` 由 `GPIOB` 改为 `GPIOA`（用户自己改的，落在 **PA1**，正好是 `TIM2_CH2` 默认映射，反而省了重映射）。
  2. 超声波最终定为 **`Trig=PB10`、`Echo=PB11`**（见 C-08），两个冲突一起消失。
- **验证**：`check_pins.ps1` 输出「27 个引脚，0 冲突，all clear」。
- **涉及文件**：`Chassis_2026/config/pin_config.h`
- **教训**：引脚表改动后**必须先跑 `check_pins.ps1` 再编译**，否则冲突要到上电冒烟才发现。

## C-02 编译报 `BOARD_LINE_B_CH6_PIN undeclared` ✅

- **发现阶段**：S0
- **现象**：`bsp/bsp_line_gpio.c:20: error: 'BOARD_LINE_B_CH6_PIN' undeclared here (not in a function); did you mean 'BOARD_LINE_B_CH7_PIN'?`，整个工程编不过。
- **根因**：循迹引脚表的 `CH6` 条目引用了 `BOARD_LINE_B_CH6_PIN`，但 `pin_config.h` 里只定义了 `BOARD_LINE_CH6_PIN`（A 组）。宏名对不上，编译器当成未声明标识符。
- **解决**：
  1. 引脚表 `CH6` 改为 `{ BOARD_LINE_GPIO, BOARD_LINE_CH6_PIN }`（= PA15）。
  2. `BSP_Line_Init()` 拆成两次 `GPIO_Init`：`CH1~CH6` 走 `BOARD_LINE_GPIO`（GPIOA），`CH7` 单独走 `BOARD_LINE_B_GPIO`（GPIOB，PB3）。
- **涉及文件**：`Chassis_2026/bsp/bsp_line_gpio.c`
- **教训**：宏改名必须全工程 grep 一遍（`grep -rn "BOARD_LINE" .`），这个错在编译期暴露已经算运气好。

## C-03 TIM2 部分重映射导致编码器读数恒 0 ✅

- **发现阶段**：S1 编码器自检
- **现象**：手推左轮，串口行 `enc=` 始终是 `0`，不报任何错。
- **根因**：`bsp_encoder.c` 里有一行 `GPIO_PinRemapConfig(GPIO_PartialRemap1_TIM2, ENABLE)`。它把 `TIM2_CH1/CH2` 从 PA0/PA1 挪到 **PA15/PB3**，而实际接线在 PA0/PA1 —— 定时器数的是两个没人接的脚。
- **解决**：删掉这一行。E1 就在 PA0/PA1，用的是 **TIM2 默认映射**，根本不需要重映射。同时保留 `GPIO_Remap_SWJ_JTAGDisable`（CH6=PA15、CH7=PB3、STOP=PB4 都是 JTAG 脚，不关 JTAG 这几个脚不能用，**而且同样不报错**）。
- **验证**：自检 `enc=` 随推轮变化。
- **涉及文件**：`Chassis_2026/bsp/bsp_encoder.c`
- **教训**：STM32 的复用功能**配错了不会报错，只会静默不工作**。配 TIM 输入前先确认「引脚 ↔ 通道 ↔ 是否重映射」三者一致。

## C-04 左右编码器符号相反 ✅

- **发现阶段**：S1 编码器自检（用户实测）
- **现象**：手推轮子读出 —— 不动 `0/0`；左轮前推 `162/0`；左轮后推 `-290/0`；右轮前推 `0/-147`；右轮后推 `0/320`。**左轮前进为正，右轮前进为负**。
- **根因**：两侧电机镜像安装，A/B 相相对转向天然反号；也可能是右轮 A/B 接反（两种成因现象完全相同）。
- **解决方法**（2026-11-14，做 P1 时一并解决）：不在 BSP 里改，而是在 `modules/speed_loop.c` 换算速度时乘符号 ——
  `CHASSIS_SPEED_SIGN_LEFT = -1`、`CHASSIS_SPEED_SIGN_RIGHT = +1`（在 `config/motor_pid_config.h`）。
  理由：BSP 只管搬原始计数，极性属于「控制层怎么理解它」；而且速度约定是「正 = 后退」，
  与占空比同向，左轮前进时计数为正 → 必须取反，右轮前进时为负 → 取正。
- **验证**：`Motor_GetLeftSpeed()` / `Motor_GetRightSpeed()` 输出到串口 `sp=`，
  前进时两轮都应显示**负值**（如 `sp=-200/-200`）；若一正一负，说明某个 SIGN 配错。
- **涉及文件**：`Chassis_2026/config/motor_pid_config.h`、`Chassis_2026/modules/speed_loop.c`

## C-05 距离环符号反了 ✅

- **发现阶段**：S3-B 电机层实测
- **现象**：车距 **<100 cm 时两轮前进**、**>100 cm 时两轮后退** —— 完全反了。
- **根因**：误差写成 `dist - target`（远=正），但本车 `Motor_SetSpeed()` **正值 = 后退**。两个负号本该抵消，结果叠加成了正反馈。
- **解决**：`error_cm = CHASSIS_FOLLOW_TARGET_DISTANCE_CM - DistanceSensor_GetCm()`（近=正=后退），第 102 行加中文注释，第 116 行注释同步为「误差为正 = 太近 = 后退」。
- **验证**：60 cm 后退 / 140 cm 前进 / 100 cm 不动，三条全对。
- **涉及文件**：`Chassis_2026/application/chassis_task.c:102-104`
- **教训**：**极性必须用实机现象定，不能靠变量名猜**。同时记住：本车「正速度 = 后退」这条反直觉事实。

## C-06 差速转向反了 ✅

- **发现阶段**：S4 接真云台板后
- **现象**：`Dev` 为正（云台朝右转去对准人）时，车却往左拐。
- **根因**：差速合成方向与本车「正速度=后退」的极性不匹配。
- **解决**：`left = forward_speed - steer; right = forward_speed + steer;`（原来是 `+ / -`），并在上方加注释说明「车头右转 = 左轮更负、右轮更正」。
- **验证**：`dev 30` → 右转、`dev -30` → 左转，负反馈收敛。
- **涉及文件**：`Chassis_2026/application/chassis_task.c:148-149`
- **遗留风险**：现在**取反点有两个** —— 差速合成 与 `CHASSIS_FOLLOW_STEER_SIGN`(+1)。以后若再出现反向，**只许动一个**；彻底解法是删掉 `STEER_SIGN` 乘法只留一处（未做）。

## C-07 超声波 Echo 选脚：多数 IO 不耐 5 V ✅

- **发现阶段**：超声波选脚
- **现象**：HC-SR04 的 Echo 是 **5 V 输出**，接错脚可能打坏 MCU。
- **根因**：STM32F103 上标 `TTa` 的脚（PA0~PA7、PB0、PB1）**不是 5 V 容忍**；标 `FT` 的才是。
- **解决**：Echo 只用 FT 脚 —— 先选 PB15，后因让出引脚改为 **PB11**（GPIOB，FT）。Trig 是纯输出，用 TTa 没关系。
- **附带**：`Echo=PB11` → EXTI 线 11 → 仍属 `EXTI15_10_IRQn`，`board_config.h` 的中断号不用改（若以后改到 0~9 号线才要手改）。
- **涉及文件**：`Chassis_2026/config/pin_config.h`、`bsp/bsp_ultrasonic.c/.h`

- **发现阶段**：S2 之前
- **用户要求**：「后面不打算使用 MPU6050 模块，看看能不能把原本分配给这个模块的引脚分配给超声波模块」。

  3. 文档 `引脚分配.md` 合并成唯一一节「超声波（HC-SR04）接线」，并解释「为什么选 PB10/PB11」「为什么用 EXTI 而不是硬件捕获（PA12 没有可用捕获通道）」。

## C-09 搜索转圈时人就在旁边，车却不停 ✅

- **发现阶段**：2026-11-11 实机
- **现象**：车丢人后原地转圈找人，人就站在旁边，车仍然一直转。
- **根因**：搜索分支只在自己算「转够 5 s / 转够 3 轮」才切换状态，**没有对「突然检测到人」做任何响应**。
- **解决**：新增搜索子状态 `CHASSIS_SEARCH_STOP = 4`（串口 `srch=4`）：
  - 搜索期间只要有**一帧** `fresh`（认出人），立刻 `Motor_SetSpeed(0,0)` 停车；
  - 记下进入前的搜索子状态，需**连续** `CHASSIS_SEARCH_HOLD_MS = 300 ms`（约 10 个云台帧，必须 < 链路超时 500 ms）都看到人才真正退出搜索；
  - 中途又丢了 → 回原搜索子状态，轮数/相位不清零；
  - 加编译期检查 `#if (CHASSIS_SEARCH_HOLD_MS >= CHASSIS_LINK_TIMEOUT_MS) #error`。
- **遗留现象（🟡）**：如果 OLED 的 `OK` 只**闪一下**就回 `SRCH`，说明人只被转圈「扫过」、连续可见不足 300 ms。加大 `HOLD_MS`（比如 400）能改善，但接近 500 会与断链混淆。
- **涉及文件**：`Chassis_2026/application/chassis_task.c`、`config/motor_pid_config.h`
- **验证**：编译 FLASH 17900 B；`run_test.ps1` 37/37。

## C-10 超声测不到距离就整车停，无法只「对准」 ✅

- **发现阶段**：2026-11-12
- **用户反馈**：「摄像头识别到人，但超声波没有识别到人的时候小车就会自动停下，这是为什么」。

## C-11 原地对准时车头总偏过头 ⬜

> **状态说明**：方案已定、代码已改、编译与 PC 测试已过，但**一次实机验证都没做**，
> 所以按「未解决」记录。等上电实测确认过冲消失后再改成 ✅。

### 问题

超声无效、车进入「原地转向对准人」后，车头总是**转过去冲过头，再拐回来**。
人站在侧方 90° 时尤其明显，表现为「甩过去 → 顿一下 → 往回拧」。

### 原因

（用户最初怀疑是「超声波模块识别有延时」，这里纠正：对准分支里 `forward_speed = 0`，
**超声波根本不参与转向**，延时不在超声这一段。）

真因是**整条链路的死时间 200~300 ms**，从「人已经在那个方向」到「车真的停下」要经过：

| 环节 | 量级 |
|---|---|
| K230 曝光 + 推理 + 30 ms 帧周期 | 60~100 ms |
| 云台一阶滤波（α=0.3）+ PID 跟随 | 30~50 ms |
| 板间 30 ms 链路 + 底盘 5 ms 控制 | 35~40 ms |
| 电机斜率 50‰/拍（0→250‰ 约 25 ms）+ 车体惯性 | 50~80 ms |

恒速 250‰ ≈ 90°/s，在 0.25 s 死时间里就会多转 **约 22°** —— 正好是实机看到的过冲量。

### 解决方法（已写入代码，未验证）

把「恒速转」换成**纯比例控制 + 转速上限 + 迟滞**（2026-11-13 按用户要求，
把死区从转速算式里拿掉，只留作停车判定）：

```
a = |云台偏角|（0.1° 单位）
a ≤ 80   (8°)    -> steer = 0，停住
80 < a < 120     -> 保持上一拍状态（迟滞，防止「停一下、转一下」地点头）
a ≥ 120  (12°)   -> steer = a × 8 ÷ 10，夹 ±250‰      ← 不扣 8°
                    方向 = sign(偏角) × CHASSIS_FOLLOW_STEER_SIGN
forward_speed = 0（不前进）
```

> **两套死区互不影响**：跟随死区 `CHASSIS_FOLLOW_STEER_DEADBAND_TENTH_DEG`(7°)
> 只在「有人且有距离」的正常跟随里用；对准取 `link.yaw_dev_tenth_deg` 原始偏角，
> 停止带 8° 只决定「停不停」，不参与算速度。

| 偏角 | 输出转速 |
|---|---|
| 31° 以上 | 250‰（顶上限） |
| 30° | 240‰ |
| 20° | 160‰ |
| 12° | 96‰ |
| ≤ 8° | 进停止带 → 停 |

**为什么比例律能吃掉过冲**：越接近目标转速越低，最后几度几乎是「蹭」过去的，
死时间里多转的角度被压缩到很小；恒速转则不管还剩几度都用同一速度冲。

**为什么不用正常跟随的 `STEER_GAIN_Q`(20‰/度)**：那个增益是给「边走边跟」用的，
有前后运动做阻尼；原地对准没有阻尼，大增益 + 700‰ 上限会直接转过头。

新增的 4 个宏（`Chassis_2026/config/motor_pid_config.h`）：

| 宏 | 值 | 含义 |
|---|---|---|
| `CHASSIS_ALIGN_GAIN_Q` | 8 | 比例增益（‰/度） |
| `CHASSIS_ALIGN_DUTY_MAX` | 250 | 转速上限（‰） |
| `CHASSIS_ALIGN_STOP_TENTH_DEG` | 80 | 停止带（8°） |
| `CHASSIS_ALIGN_RESUME_TENTH_DEG` | 120 | 恢复带（12°，须 > 停止带，有编译期检查） |

## C-17 跟随「改一个坏一个」：结构性问题，非参数问题 🟡

## C-18 占空比 ≠ 速度：开环导致「参数永远调不准」 ✅（代码已改，待实机）

- **发现阶段**：P1（`docs/模式2控制重构方案.md` 的根因 A）
- **现象**：同一套参数，电池满电时车冲得太快、亏电时又跟不上；地毯和地砖表现完全不同；每次「调好」的参数换一天又不对。
- **根因**：`Motor_SetSpeed(x)` 的 `x` 是**占空比**（PWM 百分比），而轮子的实际转速 = `f(占空比, 电池电压, 地面摩擦, 载重, 电机温度)`。占空比固定时速度并不固定，被控对象一直在漂，开环比例参数当然调不准。
- **解决方法**：加**轮速闭环**（内环），外环不变。
  - 新增 `Chassis_2026/modules/speed_loop.c`：编码器增量 → 实测速度 → PI → 占空比；
  - 前馈取目标值本身（按标定，稳态「speed ‰」≈「duty ‰」），PI 只修残差 —— 这样 `KI` 很小也不会「起步半天不动」；
  - 抗积分饱和：输出被夹住且误差还在同向推时，撤掉本拍积分；
  - 静摩擦补偿：有目标就至少给 `CHASSIS_SPEED_MIN_DUTY`，否则电机不转、PI 把积分顶满；
  - **PI 每 4 拍（20 ms）算一次**：5 ms 里编码器只走十几个计数，1 个计数≈几十‰，5 ms 算一次会跟着量化噪声抖；
  - `Motor_Stop()`/上电时 `SpeedLoop_Reset()`：清积分并丢弃停车期间攒的增量，否则起步第一拍会读到巨大假速度而反向踢一下。
- **参数**（当前值，全在 `config/motor_pid_config.h`）：`CHASSIS_SPEED_LOOP_ENABLE`=1（改 0 即退回开环）、`CHASSIS_SPEED_LOOP_DIV`=4、`CHASSIS_SPEED_CNT_FULL_PER_SEC`=**9000**、`CHASSIS_SPEED_KP`=**0.12**、`CHASSIS_SPEED_KI`=**0.4**、`CHASSIS_SPEED_INTEG_MAX`=700、`CHASSIS_SPEED_MIN_DUTY`=70、`CHASSIS_SPEED_DUTY_SLEW`=**150**（‰/20 ms 窗口）、`CHASSIS_SPEED_MEAS_MAX`=**1500**、`CHASSIS_SPEED_SIGN_LEFT`=-1、`CHASSIS_SPEED_SIGN_RIGHT`=+1。
- **首轮实机失败（2026-11-14，第一版 3000 / 0.7 / 2.5）**：串口只看到 `out` 从 `263/215` 一路冲到 `700/-700`、`sp=±2000`，而 `dist` 一直停在 29~32 cm 不变 —— 车不是在前/后走，是**原地扭**。
  - 机制（「闭环自己跟自己打」）：目标只有 +305‰，实测却读到 +2083‰（标定偏小 3 倍）；误差 -1778 经 `KP=0.7` 变成 -1245‰ 修正，比物理上限还大 → 输出夹到 **-700 反向全速**；轮子真反过来后实测变号，输出又顶 **+700**，在两个极端之间来回拉满。左右两轮起步差半拍，于是一个已反、一个未反（`-2083/+2017`），车被扭起来。
  - 反推标定：`out≈700` 时 `sp≈2050` → 满占空比约 2900‰ 读数 → `CNT_FULL` 实际约 3000×2.9 ≈ 8900，取 9000。
  - 修复 4 项：标定 3000→**9000**、`KP` 0.7→**0.12**、`KI` 2.5→**0.4**、新增 `DUTY_SLEW` **150**（每个 20 ms 窗口最多变 150‰，物理上不可能瞬间反接）；附带把实测速度夹到 ±**1500**‰。
  - 为什么开环时不会这样：开环没有反馈，程序不会「看到速度再反打」。闭环一旦既看错尺度、又给太大增益，就变成正反馈。
  - **状态**：代码已改并编译通过，**等实机复测**（预期：目标 300‰ → 占空比约 100‰，平滑收敛不再拉满）。
- **验证方式**：串口 `sp=`（实测速度 ‰，正=后退）与 `out=`（占空比 ‰）。直行时 `sp` 应贴着外环目标；上坡/地毯/电池亏电时 `out` 会自己变大而 `sp` 保持 —— 这正是闭环在起作用。
- **标定**：`CHASSIS_SPEED_CNT_FULL_PER_SEC` 决定「‰ 对应多少真实车速」。**偏小很多时会出事**（读数量级放大 → 误差巨大 → PI 打满反向，见上），所以首轮就按实测反推改成 9000。精标方法：让车以固定目标速度直行 1 m，量用时 t 秒，则 `新值 = 旧值 × (1000/t) / 目标‰`。
- **副作用**：固件涨了约 2.3 KB（软浮点），修复后 FLASH **21664 B / 33.06%**，RAM 2448 B / 11.95%。

## C-19 摄像头装歪：偏角常数偏差导致车绕人转圈 ✅

- **发现阶段**：P1 实机（2026-11-14，用户发现「摄像头初始位置偏右」）
- **现象**：小偏角直行时车原地扭、绕着人转圈；串口 `dev` 长期停在 −62°、−77° 这种大角度，`out` 顶到 ±700、`sp` 反号。
- **根因**：底盘用的偏角是 `dev = (yaw − GIMBAL_YAW_HOME_DEG) × 10`，零点固定取**上电中点 135°**。摄像头与车头轴线不重合（装歪 θ 度）时，人站在车头正前方、云台已把人放到画面中心，实际 yaw = 135+θ，于是底盘收到恒定的 `dev = θ×10`。底盘把「恒定偏差」当成「人在旁边」，持续转向；车一转，人相对车头又偏，云台再追 → 绕人转圈。
- **为什么容易误判成控制问题**：这个偏差对云台自身是**无感**的（人在画面中心，误差为 0），只在跨板通信的偏角里暴露，所以调 PID、调增益都没用。
- **解决**：云台板新增零点宏 `GIMBAL_CHASSIS_ZERO_DEG`（`Gimbal_2026/config/gimbal_config.h`），`GimbalController_GetYawDevTenthDeg()` 改用 `(yaw_angle_deg - GIMBAL_CHASSIS_ZERO_DEG) × 10`。
- **标定法**（4 步）：车摆正 → 人站车头正前方 1.5 m → 按 PB13 切模式1（电机不输出，链路与云台照常）→ 读串口 `dev`，则 `新零点 = 135 + dev/10`。
- **本次标定值**：`dev = -327` → `GIMBAL_CHASSIS_ZERO_DEG = 135 + (-32.7) = 102.3f`。
- **验证**：标定后小偏角实验通过 —— 车能直线缓慢靠近，不再原地扭/绕圈。
- **注意**：若 `|dev| > 1320`（>±132°），多半是舵盘装错齿位（差 1/4 圈），应先重装舵盘再标定。
- **涉及文件**：`Gimbal_2026/config/gimbal_config.h`、`Gimbal_2026/modules/gimbal_controller.c`、`Gimbal_2026/docs/技术交付文档.md`
- **教训**：跨模块的「坐标系零点」必须显式建模并可标定；用「上电中点」冒充「机械正前方」只在装配完美时成立。

  - 整条链路死时间约 **250~300 ms**（K230 30 ms 帧 + 推理 → 云台滤波与 PID → 30 ms 链路 → 5 ms 控制 → 电机 40‰/拍的斜率 → 车体惯性）；
  - 以 80~90°/s 的转速，300 ms 就转过 **24~27°**，再加上惯性，实际过冲超过 K230 水平半视场，人就出画了；
  - 位置式 P 控制在此没有「减速段」概念 —— 它只知道「还偏着就继续转」，等到发现对准时已经晚了。
- **解决（方案 A：降转速 + 加大停止带）**：
  - `CHASSIS_FOLLOW_STEER_GAIN_Q` **7 → 4**；
  - `CHASSIS_FOLLOW_STEER_DEADBAND_TENTH_DEG` **120 → 150**（12° → 15°）；
  - 新增 `CHASSIS_FOLLOW_STEER_MAX`，在 `chassis_task.c` 3.1 段对差速单独封顶（只限转向、不限前后）；先试 150‰ → 降到 100‰（实测转得太肉）→ **调回 150‰**；
  - `CHASSIS_SPEED_INTEG_MAX` **700 → 250**，防「目标速度突然反向」时速度环积分饱和。
- **效果预估**：45° 时差速由 231‰ 降到 **150‰（当前）**，转速约 35~40°/s；300 ms 死时间内只转 10~12°，仍在视场内。
- **尝试与回退（2026-11-14）**：`STEER_MAX` 曾降到 100‰，实测转向偏肉（15~25° 区间差速只有 0~40‰），已调回 150‰。若仍嫌过冲，下一步优先降死区 150→120（让 15~25° 段有差速），而不是继续压上限。
- **已验证部分**：编译通过 FLASH **21688 B / 33.09%**，RAM 2448 B；`run_test.ps1` **37/37**。
- **还没验证的部分**：实机大偏角（45°）是否还会过冲；人绕车快走时是否「跟不上」。
- **下一步调参**：仍过冲 → 死区 150→120（先给 15~25° 段差速）或 `STEER_MAX` 150→120；大角度跟不上 → `STEER_MAX` 150→200 或 `STEER_GAIN_Q` 4→5。
- **涉及文件**：`config/motor_pid_config.h`、`application/chassis_task.c`、`Chassis_2026/docs/技术交付文档.md`、`docs/模式2实施计划.md`
- **教训**：有显著死时间的闭环里，「P 增益 × 偏差」直接当转速指令一定会过冲；必须给**转速上限**或**减速段**，否则增益再小也只是「慢一点的过冲」。

# 二、云台（Gimbal_2026 / Gimbal_1.0）

## C-21 OLED「完全不亮」：软件 I2C 超速 + 无总线复位 + 无应答检测 🟡

**发现阶段**：S5 参数整定（2026-11-14 晚）。此前 OLED 一直正常显示四行，突然完全不亮。

**现象**：屏全黑、无任何字符；串口日志仍正常输出，说明 `ChassisTask_Init()` 已跑到 `OLED_Init()`（`chassis_task.c:647`），是屏侧没有响应，不是主循环卡死。

**根因（代码级，按可能性排序）**
1. **I2C 无任何延时**：`modules/oled.c` 的 `OLED_I2C_SendByte()` 里 SCL 拉高后立刻拉低，`GPIO_WriteBit` 一次调用约 10~15 个周期，72 MHz 下 SCL ≈ **2~2.5 MHz**，SSD1306 规格上限 **400 kHz**，超出 5~6 倍。余量不足的模块表现为「上电有时能初始化、有时白屏」。
2. **无总线死锁恢复**：MCU 在传输中途复位（频繁烧录必然发生）时，SSD1306 会卡在「等第 9 个时钟」并拉住 SDA，之后全部通信失效，**只能给屏断电**。`OLED_Init()` 原来直接从 0xAE 开始，没有 9 时钟 + Stop 的解锁序列。
3. **无应答检测**：`OLED_I2C_SendByte()` 注释明确写「不处理应答信号」，因此软件无法区分「屏没接 / 没供电 / 地址错 / 总线死」。
4. `GPIO_Speed_50MHz`：100 kHz 级总线配 50 MHz 驱动能力，边沿过陡，长杜邦线上易振铃误码。

**解决（2026-11-14）**
- `modules/oled.c`：新增 `OLED_Delay()`（`OLED_I2C_DELAY_NOP 4U` 个 `__NOP`，约 0.4 µs 半周期 → SCL ≈ 1.2 MHz），在 Start/Stop/每个 SCL 边沿/应答位后调用；`OLED_I2C_SendByte()` 改为**返回值 = 应答**（第 9 时钟释放 SDA 后读 `IDR`）；`OLED_WriteCommand/WriteData` 用地址字节的应答刷新 `s_oled_present`；`OLED_Init()` 开头插入 **9 个 SCL 时钟 + 一个 Stop** 的总线复位；新增 `OLED_IsPresent()`。
- `bsp/bsp_soft_i2c.c`：`GPIO_Speed_50MHz` → `GPIO_Speed_2MHz`；新增 `BSP_SoftI2C_ReadSda()`（读 `GPIO_ReadInputDataBit`，开漏下必须读 IDR）。
- `bsp/bsp_soft_i2c.h` / `modules/oled.h`：声明两个新接口。
- `application/chassis_task.c`：串口调试行末尾追加 `oled=%u`（`OLED_IsPresent()`），**一眼判断屏有没有应答**。

**验证**：FLASH **22000 B / 33.57%**，RAM 2448 B / 11.95%，`tests/run_test.ps1` **37/37**。

**判读方法**
- `oled=1` + 屏亮 → 修好了。
- `oled=1` + 屏不亮 → I2C 通了但显示没打开，查 `0xAF`/对比度/复位脚。
- `oled=0` → 屏侧没应答：先量 VCC/GND，再把 `OLED_I2C_DELAY_NOP` 加到 8 或 16 继续降速；仍为 0 则是接线/模块问题。

**副作用**：整屏刷新从约 20 ms 变为约 30 ms（每 100 ms 一次），显示更慢但通信更稳；若后续仍嫌占 CPU，下一步是「帧缓存 + 分块推送」把阻塞拆到多拍。

**教训**：软件 I2C 抄例程时最容易漏掉的就是「延时」和「应答」；这两项一缺，故障就变成「时好时坏」，比彻底不工作更难查。

## G-01 舵机完全不响应 K230 发来的坐标 ✅

- **现象**：K230 串口在发数据，云台一动不动。
- **根因（两个叠加）**：①STM32 端还是 **8 字节**旧协议，K230 实际烧的是 **13 字节**（`AA 55 01 08` + int16 x/y + 2 reserved + XOR）；②解析器失配后原地卡死，不前进重同步。
- **解决**：解析器改成 13 字节 + **逐字节滑窗重同步**（失配只前进 1 字节）。
- **教训（我犯过的错）**：我曾因为工作区里存在一份 8 字节脚本，就断定设备在跑它。**文件存在 ≠ 设备在跑**，必须以实机报文为准。

## G-02 云台大幅摆动、来回甩 ✅

- **根因（三个叠加）**：
  1. `sign = -1` 在本闭环里构成**正反馈**，越偏越往外打；
  2. `Kd = 0.3` 在位置式 PID 里被 `Kd/dt = 100×Kd` 放大 30 倍；
  3. 两轴共用一个 `Kp`，但水平/垂直视场差 2.3 倍。
- **解决**：推倒重写为「一阶低通 + 软死区 + 常规位置式 PID」，参数 `Kp=0.1`、`Ki=0`、`Kd=0.01`、`alpha=0.3`、`dead_zone=3.0`、`sign_x=sign_y=-1`。
- **我犯过的错**：反复用「人往右走云台该往右转」这种**开环判据**去定 `sign`，在闭环里取反会直接发散。**唯一有效判据是「偏差是否收敛到 0」**。

## G-03 轴映射错：人水平移动，动的却是俯仰舵机 ✅

- **现象**：人在画面里左右走，动的舵机是上下那个。
- **根因**：一直靠函数名（`angle_on`/`angle_down`）猜物理轴，猜错。
- **解决**：以实机现象定版 —— `PA1` 接**左右旋转 270°**（`angle_on`/`yaw`）、`PA0` 接**上下俯仰 180°**（`angle_down`/`pitch`）；画面 x 走 yaw、y 走 pitch。
- **教训**：函数名不是证据，接线和现象才是。

## G-04 `Serial_GetTickMs()` 基本不递增 ✅

- **现象**：上电后毫秒时基跳一次就「死住」，导致 `Vision_IsTargetFresh(300)` 恒成立 —— **K230 断线也判不出丢失**。
- **根因**：`Delay_us` 每次都 `SysTick->VAL = 0` 并重装 `LOAD`，再读 VAL 差值恒为 0，毫秒计时自然不涨。
- **解决**：`Delay_us` 末尾累加 `s_us_pending` → `s_tick_ms`，新增 `uint32_t Delay_GetMs(void)`；`Serial_GetTickMs()` 改为 `return Delay_GetMs();`，`Serial_TickUpdate()` 变空实现（保留函数以不改 `main.c`）。
- **涉及文件**：`Gimbal_1.0/System/Delay.c`、`Hardware/Serial.c`

## G-05 云台板实际接线与旧工程不符 ✅

- **现象**：云台板 PCB 上舵机接口是 **PA8 / PA11**，旧工程是 PA1 / PA0 + TIM2。
- **解决**：改为 **`TIM1`**：`PA8 = TIM1_CH1 = 俯仰 180°（云台上）`、`PA11 = TIM1_CH4 = 旋转 270°（云台下）`；**高级定时器必须 `TIM_CtrlPWMOutputs(TIM1, ENABLE)` 打开 MOE**，否则完全没有波形。
- **验证**：编译 FLASH 16140 B；TIM1 无冲突（`Delay.c` 只用 SysTick）。
- **涉及文件**：`Gimbal_2026/config/pin_config.h`、`config/board_config.h`、`bsp/bsp_servo_pwm.c`

## G-06 开启 CCR 预装载多出 10~20 ms 延迟 ✅

- **现象**：与 `Gimbal_1.0` 逐行对比时发现 `Gimbal_2026` 多了 `TIM_OC1PreloadConfig`/`TIM_OC4PreloadConfig`。
- **影响**：占空比要等下一个更新事件才生效，多 10~20 ms 延迟 —— 在视觉伺服里是可观的相位滞后。
- **解决**：删掉这两行及其注释，保留 `TIM_ARRPreloadConfig`。StdPeriph 的 `TIM_OC1Init` 本身不置 `OC1PE`，删掉后 `TIM_SetCompare1/4` 立即生效，与旧工程行为一致。
- **涉及文件**：`Gimbal_2026/bsp/bsp_servo_pwm.c`

## T-01 ST-Link V2J23S4 报 `init mode failed`，烧不进去 ✅

- **现象**：`make flash` 输出
  `Info : STLINK V2J23S4 (API v2) VID:PID 0483:3748` / `Info : Target voltage: 3.262850` / `Error: init mode failed (unable to connect to the target)`。
- **我最初的误判**：怀疑接线、双电源、SWD 速度。用户判断是 ST-Link 固件问题，确认是**银色铝壳山寨棒**。
- **真根因**：**OpenOCD 0.12 的 `interface/stlink.cfg` 用 dapdirect 驱动，要求固件 ≥ V2J24**；V2J23S4 直接报 `Error: The firmware in the ST-Link adapter only supports deprecated HLA.`
- **解决**：改用 `interface/stlink-hla.cfg`，并把 `adapter speed 480` 写在 `source [find target/stm32f1x.cfg]` **之后**（写前面会被重置回 1000 kHz，1000 kHz 会报 `jtag status contains invalid mode value - communication failure`）。
- **验证**：`device id = 0x00006410`、`flash size = 64 KiB`、`reset halt`/`reset run` 均通过，不依赖 RST 线。
- **警告**：**不要**用官方 `ST-LinkUpgrade` 刷山寨棒，极易变砖，救回需要拆壳再用第二根 ST-Link 重刷。
- **遗留**：`Chassis_2026/openocd.cfg` 仍是旧配置，底盘板 `make flash` 会撞同样的错；改成 HLA 版即可（未做）。

## T-02 PC 模拟脚本报 `PermissionError(13, '拒绝访问。')` ✅

- **现象**：`python sim_gimbal_link.py --port COM5` 后，`sent` 涨到 523 就停，界面打印
  `[发送失败] WriteFile failed (PermissionError(13, '拒绝访问。', None, 5))`。
- **根因**：**串口被占用 / 适配器掉线**，与协议、固件无关（脚本里写失败就 `break` 退出线程）。
- **解决**：重新插拔 USB-TTL，确认没有别的程序（串口助手、另一个 python）占用 COM5。
- **注意**：这台机器上 **COM3 / COM4 / COM11 / COM12 是蓝牙串口，不要选**；`COM5 = CH340` 才是 USB-TTL。

## T-03 子代理堆积（51 个），难以清理 ✅
